# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Neon Cascade: an original match-3 browser game. It's a single page application in TypeScript and Vite with **no UI framework**, using plain DOM, CSS and inline SVG. The package manager is **pnpm**; don't use npm or yarn.

This is an original game in the match-3 genre. Don't copy names, art, sounds or visual style from existing commercial games (e.g. Bejeweled).

## Commands

```bash
pnpm dev          # dev server
pnpm test         # Vitest unit tests (src/**/*.test.ts)
pnpm typecheck    # tsc, no emit
pnpm build        # tsc && vite build -> dist/
```

Before calling a change done, run `pnpm typecheck && pnpm test && pnpm build`. For visual or UI changes, also check the game in a browser at desktop and phone width (~390px).

## Deployment

Pushes to `main` deploy to GitHub Pages (https://counterall.github.io/match-three/) via `.github/workflows/deploy.yml`, which runs typecheck, tests and build first, so a red CI means no deploy. Pushes and PRs that change only Markdown files (`**/*.md`) skip the workflow entirely (no build, no deploy); run it by hand (workflow_dispatch) to force a deploy. pnpm's version is pinned by `packageManager` in `package.json`; keep it in sync with the lockfile. Keep `base: './'` in `vite.config.ts`.

## Development workflow

Every change, from an issue or a direct request, follows the same loop.

1. **Worktree per change**, off the latest `origin/main`: `git worktree add ../bejeweled-worktrees/<branch> -b <branch> origin/main`, then `pnpm install --frozen-lockfile` in it. Branches are `issue-<n>-<slug>` for issues and a short slug (e.g. `bigger-board`, `gem-style`) for direct requests. Never develop in the main checkout; a dev server may be running from it.
2. **Visual work gets a preview first.** For new artwork or a look the user must judge (e.g. the animal gems), publish a standalone preview page (every theme, real board sizes), and iterate on it until the user approves, before touching game code.
3. **Tests first.** Turn the acceptance criteria into Vitest tests, confirm they fail for the right reason, then implement. Update existing tests only where the change intends it. CSS and HTML are tested as text (`?raw` imports; there is no DOM in Vitest).
4. **Verify:** `pnpm typecheck && pnpm test && pnpm build`, then the browser check below for anything visible or timed.
5. **Independent review:** a separate reviewer agent gets the requirement, the worktree and the diff, but not the implementer's reasoning. Fix must-fix and should-fix findings that hold up, re-verify, and list declined findings with reasons in the PR.
6. **Ship:** commit (what and why; `Closes #<n>` for issues), rebase on `origin/main`, push the branch, open a PR with **What changed**, **Behaviour choices to review** and **Testing** (commands, engines, gaps, declined findings). For direct requests, let the user try a local build (preview server on a spare port) and wait for their go-ahead before committing or pushing.
7. **Never merge, never push to `main`.** The user reviews and merges. After a merge, remove the worktree and branch (`git worktree remove …`, `git branch -D …`) and `git pull --ff-only` in the main checkout.

Ambiguity: pick the reasonable option and list it under "Behaviour choices to review". Ask first only for choices that are hard to undo (saved settings format, removing a feature).

### Issue workflow specifics

GitHub issues are worked by the `/github-issues` skill, usually on an hourly `/loop`. Each run triages open issues and PRs, cleans up worktrees of merged PRs, and handles at most two issues (in separate worktrees, in parallel only if they touch different files). If nothing is open, it reports that in one line and stops.

- Verify: `pnpm typecheck && pnpm test && pnpm build`.
- Reviewer must check: everything in Architecture and Conventions below, especially theme tokens in every theme, i18n (every string in every language, `data-i18n` tags, English in `index.html`), no ids in `gemSvg()` output, `parseSettings` staying backward compatible, `prefers-reduced-motion`, and layout at 320–390px.
- Dev-server ports to avoid: 5173, 4317, 4318 (the user's). Use another free port (e.g. 4335+) for e2e preview servers, and stop them afterwards.

### Browser checks (e2e)

- `playwright-core` installed in the session scratchpad (never as a project dependency), driving the system Chrome at `/usr/bin/google-chrome`, against `pnpm exec vite preview --port <spare> --strictPort` of the production build.
- `page.clock` for anything timed (round timer, pause, game over). CSS animations still run on real time, so wait briefly before screenshots.
- Block every non-localhost request. Set the language through the browser context's `locale` (e.g. `zh-CN`).
- Click the visible labels in Settings, not the hidden radio inputs.
- Sizes: desktop 1920×950, short laptop 1366×650, iPad 820×1180 and 1180×820, phones 390×844 and 320×640, with a six-digit score where the HUD is involved. Screenshot the key states in Neon and Pastel and look at them.
- WebKit doesn't launch on this machine, so Safari and real devices go in every PR's "not verified" list.

## Architecture

- `src/board.ts`: **pure game logic**, with no DOM access. The grid is `grid[row][col]` of `Gem | null`, of any size (`rowsOf`/`colsOf`; never assume square or 8×8) (`null` only between clearing and refilling). Randomness is injected as an `Rng` so tests can be deterministic. Put new rules (special gems, modes, scoring) here and add tests in `src/board.test.ts`. **Special gems** keep the gem's type, so they match by colour. **Bombs** (issue #28, tested in `bombs.test.ts`): `Gem.special = 'bomb'`. **Line gems** (issue #32, tested in `line-gems.test.ts`): `Gem.special = 'line'` plus `Gem.dir` (`LineDir`: `row`, `col`, `diag` = ↘, `anti` = ↗; steps in `LINE_STEP`). `planClear(grid, runs, swapped)` works out a clearing step: `made` (`Made[]`: a 5+ run makes a bomb, a run of exactly 4 a line gem in the run's direction, on the swapped gem or the one nearest the middle; a gem that is already special goes off instead), `cleared`/`blasted` (cells only a blast or beam reached), and `detonated`/`fired` (bombs blast their 3×3, line gems clear their whole line to both edges; specials they reach go off too, in queue order; a special made in the same step is never cleared). `applySpecials` flags the new specials, `blastScore` adds 10 per blasted/beamed gem + 50 per bomb + 30 per line gem × cascade, and `collapse(grid, rng, BOMB_SPAWN_CHANCE)` drops in at most one random bomb per refill (no extra `rng` calls when the chance is 0). Line gems never spawn at random.
- `src/main.ts`: rendering, input and game flow.
  - Each gem has a stable `id`, and its DOM element lives in the `els` map. `render()` moves elements to their grid positions with `transform: translate(col*100%, row*100%)`, and CSS transitions do the animation.
  - New gems from `collapse()` are created above the board (`fromRow < 0`) and then fall in.
  - Board shape is responsive: `compactQuery` (`max-width: 600px`) picks 6 cols × 8 rows, otherwise 8×8. `newGame()` writes `--rows`/`--cols` on `<body>`; CSS sizes gems, grid lines and the column width from them. Crossing the breakpoint only rebuilds the board before the first move (while the round clock hasn't started). The breakpoint is duplicated in the compact `@media` block in `style.css`, so keep the two in sync.
  - `.app` width is capped so the board's height fits the viewport (`--chrome` ≈ height of header + controls + padding). Retune `--chrome` if those change height. The HUD (title + Score, Best, Time) never wraps, since a second row would break that budget. `.app` is a size container, and when the column is narrow (`@container (max-width: 540px)`: phones, short desktop windows) the title words stack. Check desktop, a short window and ~320–390px with a six-digit score if you add to it.
  - Controls and HUD labels are **icons only** (issue #36): the five `.controls` buttons (Pause, Daily, Hint, New game, Settings) are `.icon-btn`s whose label is a `data-i18n-label` aria-label plus a `title` tooltip (`applyLanguage()` translates both; `syncPauseButton()` owns Pause's), and the Score/Best/Time labels are `.stat-icon` spans with `role="img"` (star, trophy or calendar, clock).
  - `busy` blocks input while a swap or cascade is running. `gameToken` is bumped by `newGame()` so cascades still in flight stop touching the board.
  - Animation timings are TS constants pushed to CSS as `--swap-ms` / `--pop-ms` / `--blast-ms`. A gem element carries `data-special` (`bomb`/`line`) and, for line gems, `data-dir`; `drawGem(el, mark)` redraws its artwork. Each detonation adds a `.blast` flash over its 3×3, and each fired line gem a `.beam` (`showBeam`): a strip one cell thick centred on the gem, turned by `--beam-angle`, that sweeps out both ways over `--pop-ms` and glows in the gem colour (its `data-type`); the gems it clears pop as its front passes (`beamReach()` in `board.ts` gives each cell's distance, `main.ts` turns it into a `--pop-delay`, and the step waits for the last pop). Both are plain fades over `--blast-ms` under reduced motion (no pop delays). New specials get `.special-made` (pop-in). Keep TS waits and CSS durations in sync through these, and respect `prefers-reduced-motion`.
- `src/gems.ts`: SVG shape per gem type (count must match `GEM_TYPES` in `board.ts`), drawn in 3D-style layers: a coloured body, then (clipped to the shape) a diagonal light/shadow overlay and a gloss highlight. Those layers use colour-independent gradients and per-type clip paths defined **once per page** by `gemDefsSvg()`/`installGemDefs()` (called in `main.ts` before any gem renders). `gemSvg()` must not define ids, since it's repeated for every gem. No theme colours here. The only colours are the neutral white/black luminance stops in those shared gradients, a deliberate exception to the token rule. Themes tune their strength via tokens.
  - **Special gems** (issues #28, #32): `gemSvg(type, style, cast, mark)` draws the normal gem (shape or animal) plus a corner badge, in both styles: `mark = { special: 'bomb' }` adds the bomb from `public/previews/bomb.html` as a small badge (untinted; the gem shows the colour), `{ special: 'line', dir }` a round badge with a double arrow turned by `LINE_BADGE_ANGLE[dir]`. Badges are `<g>`s, not nested `<svg>`s (a nested `<svg>` would get every `.gem svg` rule twice). Colours are `--bomb-*`/`--blast-*`/`--line-badge-*`/`--beam-core` tokens; the spark's fire gradient (`gem-fire-grad` in the shared defs) is a second fixed-colour exception. Tested in `bomb-render.test.ts` and `line-render.test.ts`.
- `src/animals.ts`: the **Animals** gem style, picked by the `gemStyle` setting. Each `Animal` is a list of `[element, litColour, shadedColour]` parts in a 100×100 box. `ANIMAL_POOL` holds **eight** animals (one more than `GEM_TYPES`); `SPARE_ANIMALS` keeps finished drawings that are not used on the board (the golden retriever, issue #20). Each game draws a cast with `drawCast(rng)`: `GEM_TYPES` distinct pool indices, index = gem type. `main.ts` keeps it in `animalCast`, redraws it in `newGame()`, and passes it to `gemSvg(type, style, cast)` in `gems.ts`, which dispatches to `animalSvg(animal)`; shapes ignore the cast, and places with no game (the settings theme previews) use `DEFAULT_CAST`. `animalSvg()` draws the parts once lit, then again shaded and clipped to the right half (`#gem-half-right`, defined once in `gemDefsSvg()`). There is **no tile in the theme colour** behind the faces: with a random cast a colour would mean a different animal each game, so animals are told apart by their own colours and the faces' **natural hex colours are a deliberate exception** to the token rule. Tested in `animals.test.ts`. On a style change, `main.ts` (`onGemStyleChange`) redraws every board gem in place with the current cast and `settings-ui.ts` redraws the theme previews.
- Diagonal matches (issue #30): `findRuns`, `findMove`, `createBoard` and `shuffle` take `MatchOptions` (`{ diagonal }`, default off). With it on, runs along both diagonals count too (each run lists its cells in order along its line, which `planClear` relies on for a bomb's middle). Swaps stay orthogonal (`isAdjacent`). In `main.ts`, `roundDiagonal` is the current round's mode, fixed by `setRoundLimit(minutes, diagonal)` in `newGame()`; every board call passes `matchOpts()` (`diagonal.test.ts` checks this). A change to the setting starts a fresh game straight away only before the first move (`onDiagonalChange`), otherwise at the next game. There is no on-screen mark for the mode (the ⤢ badge was removed in issue #36).
- `src/combo.ts`: combo callouts (issue #34), pure and tested in `combo.test.ts`. `comboTier(step)` (0 on step 1, then 1–4, capped from step 5), `calloutKey(tier)` (`comboNice`…`comboIncredible`), `stepCallout(step, plan.made, grantedBonus)` (tier, Bomb!/Line! tags each once, bomb first, and bonus seconds; null when there's nothing to say), `calloutMs` (1.1s; tier 4 and the move total 1.4s) and `showMoveTotal(steps)` (from `MOVE_TOTAL_MIN_STEPS` = 3). In `main.ts`, `resolveCascades` toasts each step's callout through `calloutContent()` and adds up `moveTotal`; once the board settles it shows *Move +n* unless there are no moves left ("No moves" wins). `toast()` builds a `.callout-word` line and a `.callout-sub` line (`.callout-chip`s + `.callout-extra`) and sets `data-tier` (`1`–`4`, `total`; none for plain toasts). CSS: `--callout-1…4`, `--callout-word` (share of the tier colour in the word: Neon 100%, Pastel 0% = ink), `--callout-tint` and `--callout-border` per theme; the pill pops in (`callout-pop`), tiers 3–4 pulse with `--glow`, and reduced motion only fades.
- `src/settings.ts`: settings model (`THEMES`, `GEM_STYLES`, `TIME_LIMITS`, `language`, `diagonal`, `parseSettings`, load/save under `neon-cascade:settings`). Pure, tested in `settings.test.ts`. `parseSettings` validates each field on its own and falls back to its default, so older saved settings keep working. `settings-ui.ts` wires the native `<dialog>` in `index.html` and returns the live `Settings`. It reports dialog open/close, gem-style, time-limit, diagonal and language changes through hooks (`initSettings({ onOpenChange, onGemStyleChange, onTimeLimitChange, onDiagonalChange, onLanguageChange })`). Add new settings as extra `<section>`s and fields on `Settings`.
- `src/i18n.ts`: UI text, **English and Simplified Chinese** (`LANGUAGES`, `MESSAGES`, `t(lang, key, params)` with `{name}` placeholders, `detectLanguage(navigator.languages)`: any `zh*` → `zh-CN`, else English). Pure apart from `applyLanguage()`, tested in `i18n.test.ts`. Static text in `index.html` carries `data-i18n="key"` (text) or `data-i18n-label="key"` (`aria-label`) and ships the **English** text, and the tests enforce both, plus that no untagged text is left. Text built in TS goes through `t(settings.language, …)` (toasts, the pause button's label); generated markup adds `data-i18n` (and `data-i18n-n` for `{n}`) so a language switch re-translates it live, and `onLanguageChange` in `main.ts` refreshes what it wrote itself. Add every new string to **every** language. The game's name stays untranslated. The saved `language` setting falls back to the browser's language. The inline script in `index.html` repeats that choice before first paint (a test keeps it in step with `detectLanguage`), sets `<html lang>`, and for non-English marks `<html data-i18n-pending>`, which hides the body until `applyLanguage()` has replaced the shipped English text. The pause button's `aria-label` is the one untagged label: `syncPauseButton()` owns it.
- `src/timer.ts`: round timer rules, pure and tested in `timer.test.ts`, with time passed in as `now` (ms). `Countdown` starts on demand and is paused by named holds (`hold`/`release`, e.g. `'settings'`, `'hidden'`). `bonusSeconds(prev, next)` gives +20s per 1000-point threshold crossed. In `main.ts` the clock starts on the first swap and is read with `performance.now()` on a `TICK_MS` interval. When it hits zero, `timeUp` blocks input like `busy`. A cascade already running finishes and scores, but earns no more bonus time, then the game-over overlay shows. A new time limit applies at the next `newGame()`, or straight away while the clock hasn't started.
- `src/best.ts`: best scores, **one per time limit** (issue #22), saved under `neon-cascade:best:<minutes>m` (`bestKey`), and for diagonal-match games under `neon-cascade:best:<minutes>m:diag` (issue #30). The pre-#22 shared key `neon-cascade:best` (`LEGACY_BEST_KEY`) is left in storage untouched and not carried over, since its round length is unknown. `loadBest`/`saveBest` take a `() => storage` getter and swallow storage errors. Tested in `best.test.ts`. In `main.ts`, `roundLimit` is the current round's length and `setRoundLimit()` loads its best into the HUD and `bestAtStart`; it runs in `newGame()` and when the time limit changes before the clock has started, so a limit picked mid-round only switches the Best shown at the next game.
- `src/daily.ts`: **daily challenge** (issue #36), pure and tested in `daily.test.ts` (UI/wiring as text in `daily-ui.test.ts`). Dates are local `YYYY-MM-DD` strings (`dailyDate(now)`); arithmetic (`addDays`, `weekdayOf`) goes through UTC midnights. `seededRng(date, rows, cols)` (FNV-1a + mulberry32) feeds **everything random in a daily round**: `drawCast`, `createBoard`, every `collapse` and `shuffle` (hints use no randomness), so the same date and board shape give the same board and the same refills for the same moves. `twistFor(date)` by weekday (Mon/Thu classic, Tue/Fri diagonal, Wed/Sat bomb rain = `BOMB_RAIN_CHANCE` 1/4, Sun both), `twistRules()` turns it into `{ diagonal, bombChance }`; a daily is always `DAILY_MINUTES` (3). Results live under `neon-cascade:daily` = `{ v: 1, days: { date: best }, streak: { last, count } }` (`parseDaily`/`recordDaily`/`streakOn`/`loadDaily`/`saveDaily`; 60 days kept; corrupt data reads as empty). In `main.ts`, `mode` (`'free' | 'daily'`) is set by `newGame(mode)`; `roundRng`/`roundBombChance` are the round's generator and bomb chance (free play: `Math.random`, `BOMB_SPAWN_CHANCE`). A daily ignores the time-limit and diagonal settings (`onTimeLimitChange`/`onDiagonalChange` only act in free play), never calls `saveBest`, and is recorded only when its time runs out (`showGameOver` → `recordDaily` for `roundDate`, the date it started). `setRoundBest()` loads the free-play best or today's daily best and flips `#best-label`'s `data-mode` (trophy ↔ calendar icon) and aria-label. `syncDailyButton()` keeps `#daily`'s `aria-pressed` and its not-played-today dot (`data-unplayed`). `announceDaily()` shows the "Daily · weekday" callout with the twist. The game-over card's daily lines (`#daily-title`, `#today-best`, `#streak`, `#free-play`) are hidden in free play.
- `src/pause.ts`: pause rules, pure and tested in `pause.test.ts`. `canPause` allows it only after the clock has started and before time's up. `shouldAutoPause` covers a page/app becoming hidden. In `main.ts`, `paused` blocks input like `busy`/`timeUp`, and `setPaused()` holds the clock (`'paused'`), clears selection/hints, disables Hint and shows the `#paused` overlay: a light tint over the still-visible board (issue #15 asked to see it; no blur), with the text on a solid `.overlay-card`. `pause-overlay.test.ts` guards both. `visibilitychange` (hidden) and `pagehide` auto-pause. Coming back stays paused until **Resume**. `newGame()` always unpauses, but only *after* `clock.reset()`, since `setPaused()` runs `updateClock()`, which would end the new round on the old expired clock. `pause()` refreshes the clock first, so a pause in the last tick can't overlap game over. A cascade running when you pause still finishes and scores behind the overlay. `syncPauseButton()` keeps the `#pause` icon button's `disabled`, `data-paused` (icon swap) and `aria-label` (Pause/Resume; deliberately no `aria-pressed`) in step. Call it whenever `clock.isStarted`, `timeUp` or `paused` changes. The game-over and paused overlays share the `.overlay` styles.
- `src/input.ts`, `src/motion.ts`, `src/cascade.ts`, `src/a11y.ts` (issue #38): pure helpers pulled out of `main.ts`, each tested. `input.ts`: `inputBlocked`, single-pointer drags (`beginDrag`/`ownsDrag`, primary button only), `swipeTarget`, keyboard `moveFocus`/`pickAction`. `motion.ts`: timings for normal and reduced motion; `main.ts` re-reads them when the `prefers-reduced-motion` query changes and pushes `--swap-ms`/`--pop-ms`/`--blast-ms`. `cascade.ts`: pop delays and the wait of a clearing step. `a11y.ts`: gem accessible names (shape or animal, special kind and direction, row/column; i18n keys in every language).
- Keyboard and screen readers (issue #38): `#board` is `role="group"`; each gem is a `role="button"` with `aria-label` (kept current by `labelGem()` on move, redraw and language change) and `aria-pressed` when selected. One gem is the tab stop (`focusPos`, roving tabindex set in `render()`); arrows move focus, Enter/Space select or swap, Escape unselects. `#score-live` (`.sr-only`, `role="status"`) announces the score once per move, apart from the toast. `shuffle()` returns false when it had to install a new board, and `main.ts` then rebuilds the elements.
- `src/style.css`: **themes are token sets** on `[data-theme="…"]` (neon, pastel). `<html data-theme>` holds the active one; theme preview cards set their own `data-theme` to preview locally. Gem colours are `--gem-0…6`, mapped to `--c` (outline) and `--fc` (body fill; optional per-theme `--gem-N-body` override) by `[data-type="N"]` rules. 3D strength per theme: `--gem-shade`, `--gem-gloss`, plus `--gem-fill-opacity`. Gems at rest have **no CSS `filter`** (no glow or drop shadow) so they stay crisp. Only the selected and pop animations add a temporary highlight glow. Glows scale with `--glow` (0 = flat). Never hard-code colours outside the token blocks, and when adding a token define it in **every** theme. A small inline script in `index.html` applies the saved theme before first paint.

## Static assets and icons

- `public/` is copied as-is into `dist/`. In `index.html`, reference these files with root-absolute paths (`/icon.svg`); Vite rewrites them to `./icon.svg` because of `base: './'`. Inside `manifest.webmanifest`, use paths relative to the manifest (`icon-192.png`, `start_url: "./"`), never `/…`, so the site works under the Pages sub-path.
- `public/icon.svg` is the source for the favicon and the PNG app icons. After editing it, run `scripts/icons.sh` (headless Chrome, no dependencies) and commit the PNGs. Keep the background opaque and full-bleed and the artwork within the central 80% circle (maskable safe zone).

## Conventions

- `strict` TypeScript with `verbatimModuleSyntax`: use `import type` for type-only imports.
- Keep logic testable: no DOM in `board.ts`; helper functions should take a grid and mutate it or return results.
- Use percentage sizes inside the board so it scales. Beware that percentage `padding`/`margin` is measured against the *board's* width, not the gem's.
- Wrap `localStorage` access in try/catch.
- Mobile zoom: `html { touch-action: manipulation }` stops double-tap zoom page-wide, and `.board` keeps `touch-action: none` for swipes. Don't add `user-scalable=no`/`maximum-scale` to the viewport meta in `index.html`, since pinch zoom must keep working in a browser tab for accessibility (it works outside the board). `src/zoom.test.ts` guards all three. It reads `style.css?raw`, which only works because `vite.config.ts` opts `style.css` into Vitest's CSS handling (`test.css.include`).
- iOS home-screen app: double-tap zoom was reported to still happen there despite `touch-action` (issue #9). So `src/tap-guard.ts` (`installStandaloneZoomGuards()`, called at startup in `main.ts`) runs **only when `navigator.standalone === true`**, which is iOS-only, so Android installs and browser tabs keep pinch zoom. It locks the viewport scale at runtime, then cancels any `touchend` that comes within `DOUBLE_TAP_MS` of the previous one and replays `click()` on the control it hit (`CLICKABLE`). Board input uses pointer events, which a cancelled touchend doesn't affect. The logic, including the handler (on fake events), is tested in `tap-guard.test.ts`.
- Commit or push only when asked, or as step 6 of the workflow above.
